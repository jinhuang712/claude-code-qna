# /qna · v1 定稿

状态：v1 已定稿并实装，无待审项。最后一次与实装对账 2026-07-27 16:42:05（北京时间，下同）。

代码侧的机械保证由 `tests/smoke.sh` 逐条断言（120 条）：选项下限与上限、preview 必填、`--where` 必须落到真实 file:line 或原话、归档必须带原话、四条命令的路径全注入、marker 的生效范围与自然过期、目录懒建。prompt 侧（R3 / R5 / R6 / R7、五类来源的召回、对账判断）无法脚本化，只能在真实会话里验。

**两条召回路径，同一个硬闸。** 记录侧在决策发生的当下经 `qna-add` 落盘；扫描侧在 `/qna:ask` 时把过滤后的存活项**同样经 `qna-add` 落盘**（带 `--found-by-scan`）。于是「备选 / 代价 / 意外」这三道过滤在两侧都由脚本兜底，拒绝即答案。两侧唯一的差别写在 `Source` 字段里：`agent` 的备选是当时真比较过的，`scan` 的是事后补的——同一条门槛，不同的成色，文件里分得清。

## 一 · 目标

20 条，每条独立可验，各自有承担者。无孤儿目标，无孤儿规则。

### 交互形态

| | 目标 | 失败长什么样 | 承担者 |
|---|---|---|---|
| G1.1 | 回答全程零打字——每题以候选项呈现，自由文本只作 Other 兜底 | 出现"你想用哪种？"这类散文提问 | **R7**（已采纳）|
| G1.2 | 题干与选项同屏——读题不需要向上滚 | 解释过长，把选项挤出视野 | R5 |
| G1.3 | 作答不打断阅读——输入动作不会让题目消失 | 退回 markdown 列表，打字时题目滚走 | R1 |
| G1.4 | 不需要你维护编号对应——不用手写 `Q1: … Q2: …` | 一次抛出 N 题让你自己对号入座 | R1 |
| G1.5 | 可以分段作答——4 题一批，答完能停 | 所有问题一次性倾倒 | R1 |

G1.3 / G1.4 / G1.5 **同源**，根因都是"装不下就退回文本墙"，一条 R1 同时堵三个。这是 R1 写成禁令级的理由。

**R7 已采纳。** G1.1 原本挂在 R2 下，但 R2 只禁是非题、R1 只禁 markdown 列表——**一句散文提问既不是列表也不是是非题，从整张规则网里漏出去了**。故新增 R7：一切提问必须走 `AskUserQuestion`，不得以散文形式提出。

### 问题质量

| | 目标 | 失败长什么样 | 承担者 |
|---|---|---|---|
| G2.1 | 每题都给成型的做法——选完就能落地 | `Q1: 太简略了`——说完"不对"还得自己想方案 | R2 |
| G2.2 | 题干自解释，不假设共享上下文 | `Q9: 根本不知道这是啥` | R3 + R2 末位选项 |
| G2.3 | 选项是真实权衡过的，不是临场编来凑数 | 选项之间没有实质差别，或明显只有一个能选 | `qna-add --alt` |
| G2.4 | 结构性差异看得见实物 | 你只能用"太简略了"这种形容词表达不满 | R4 |
| G2.5 | 一次只装载一个问题的上下文 | 一屏里塞三个互不相关的重决策 | R5 |
| G2.6 | 答案天然可多选时，一次勾完 | 被迫拆成连串"要不要 A / 要不要 B"；或只能选一个，再走 Other 打字补充 | D13 例外条款 |
| G2.7 | 长内容有地方放——细节下沉到右侧 `preview` 面板 | 为压缩解释而**丢信息**；或为保信息把题干撑成一面墙 | R4 + R5 联合 |

G2.6 有两重作用，不只是便利：拆成连串"要不要"就是**批量生产是非题**（撞 R2）；只能单选再打字补充就**破了零打字**（撞 G1.1）。所以 D13 的「默认 single-select」必须带一个真实可用的例外口，不能写死。

G2.7 是 R5 能成立的前提。R5 要求"解释 ≤150 字"——**若没有 `preview` 承接，那就是删信息，不是挪信息**。preview 是细节的去处：想看的在右侧，不想看的不占屏幕。这也直接支撑 G1.2（题干与选项同屏）：屏幕之所以够用，是因为长内容被移到了旁边而不是被砍掉。

**R4 已扩面（已采纳）：所有题默认带 `preview`。**

- 格式 / 结构 / 配置 / 数据类问题：**必须**用 preview 并排展示实物
- 其余所有题（重头题与顺手题一律）：**默认**带 preview，承接被 R5 挤出解释的细节
- **没有豁免口。** 单选题一律必须带 preview，由 `PreToolUse` 机械校验

**"没东西可放"不是一种情况，是一个信号。** 任何选项都至少有"选了会得到什么"可展示——实物、后果、演变、对比、场景实例。如果你想不出往 preview 里放什么，那不是这道题不需要 preview，是**你还没把这个选项的后果想清楚**。与 `--alt` 同理：编不出替代项说明它不是决策，编不出 preview 说明你没想清楚选项。

**内容要求（prompt 层，防填充）**：preview 必须展示选了之后**实际会发生什么**，不得复述选项标签。「选项 A：方案 A」这种是填充，等同于没写。非代码类问题同样有东西可放——本设计文档里这道 hook 校验题就是例子，三个选项分别放了校验项清单、风险实例、预期演变。

分工照旧：**存在性由 hook 机械保证，内容质量由 prompt 约束。**

不撞 G1.2：`preview` 跟随**当前聚焦的那一个选项**渲染在右侧，不是多个面板堆叠；一批 4 题也是逐题聚焦作答，屏幕上始终只有一题一面板。

G2.3 是**唯一一条不由提问规则承担、而由记录机制承担的目标**。选项的真实性没法在提问时凭空造出来，只能在决策发生的当下存下来——这是 `qna-add` 存在的根本理由，也是它必须进 v1 的原因。

| | 目标 | 承担者 |
|---|---|---|
| G6.1 | 已经被对话解决掉的，不再问第二遍 | 对账 + `qna-resolve --quote` |

1. **收尾清单的「仍未定」为空时，不许写"无"**，必须写"本次没扫到别的"

## 二 · 非目标

| | 明确不做 | 为什么 |
|---|---|---|
| N1 | **不保证完整性** | 没有机制能强迫模型意识到自己在做决定。这是根本制约，不是待改进项。实测代价：某 54 分钟会话 84 轮对话、49 次提问，`qna-add` 零调用——协议只在第 0 轮注入过一次，之后无任何复发触发点。故 `UserPromptSubmit` hook 在**零条目**会话里每 15 轮复推一次协议（见第六节）|
| N2 | 不自动执行**没被拍板**的决策 | 用户逐题点选答完的，当轮写回并落地，不追问"要开工吗"——那一问会把他刚花掉的点击作废。只有两类活例外：scope gate 之外的，以及 N3 说的破坏性 / 不可逆的 |
| N3 | 不替代该当场问的问题 | 破坏性、不可逆、猜错就白干的仍然立刻问。停车不是不问的借口 |
| N4 | 不跨 session **搬上下文** | 文件按 `session_id` 分开写，session 是上下文的单位 |
| N4' | 未决条目跨 session **可见** | 没人拍板的问题不是上下文。同项目早先 session 的未决条目由 `SessionStart` 列出并附对应 `qna-resolve` 命令行，`/qna:ask` 一并覆盖。实测：某项目 session 结束时留下 7 条，下一个 session 一条都看不见 |
| N5 | 不做团队共享 | `.qna/` 自带 `.gitignore`（内容 `*`），连同自身一并被忽略，永不进版本库 |
| N6 | 不做决策归档 / 知识库 | 已决即删，决策内容留在对话里 |
| N7 | 不让模型自己发起问答 | 唯一命令 `/qna:ask` 设 `disable-model-invocation: true` |
| N8 | v1 不管 subagent 内部的决策 | 子 agent 是独立上下文，**两条召回路径同时失效**：收不到 `SessionStart` 注入（写入路径断），且其内容从未进过主上下文、只有一份返回摘要，`/qna:ask` 扫描也扫不到（读出路径断）。subagent 密集的工作流里这个洞很大 |

## 三 · 制约

全部已核实，非推测。

| 制约 | 后果 |
|---|---|
| `AskUserQuestion` 单次最多 **4 题** | 超过 4 题必须分批连续调用（R1）|
| 每题选项工具上限 **4 个** | 本设计再加下限：单选 3、多选 2（R2）|
| `preview` 只对 single-select 生效 | 默认一律 single-select；multiSelect 是带补偿义务的例外（见第三节之二）|
| 插件组件**强制命名空间** | 裸 `/qna` 拿不到，只能 `/qna:ask` |
| `PreCompact` 不能注入、不能驱动动作 | "压缩前落盘"是死路 |
| `Stop` 的 `additionalContext` **渲染给用户**，落成 `stop_hook_summary`，`suppressOutput` 管不住 | 这条通道上只能放写给人看的话；给模型的话一律走 `UserPromptSubmit`，它落成 `attachment`，不渲染 |
| `Stop` 的 `additionalContext` 进入**下一次**模型调用 | 模型侧晚一轮才拿到；用户侧当轮就看见。给模型的提醒改走 `UserPromptSubmit` 后没有这个时差——它在本轮开头就到 |
| `SessionStart` 能注入，matcher 支持 `compact` | 抗 compact 靠它 |
| 自定义命令已并入 skill，`commands/*.md` ≡ `SKILL.md` | 可用平铺 `.md`，frontmatter 通用 |
| 本地目录可作 marketplace | 不必建 GitHub 仓库 |
| **没有机制能强制模型意识到自己在做决定** | 根本制约。只能提高命中率，不能保证 |

## 三之二 · 单选与多选

**默认 single-select。** 这不是权宜，是让 `preview` 恒可用的前提：`preview` 只对 single-select 生效，而 R4 要求所有题默认带 preview。选单选，两条规则同时成立。

**`multiSelect` 只用于答案天然可多选的题**——「这几条里哪些其实还没定」「要加哪些字段」这类问"勾哪几个"的题。用它就等于放弃 preview，因此附带两条补偿义务：

1. 本该进 preview 的细节，全部压进各选项的 `description`
2. 题干写得比单选题更完整——没有右侧面板兜底

**禁止为省事把一组单选方案题塞成多选。** 那是白白放弃 preview，没有任何收益。

**多选的选项下限是 2，不是 3。** R2 的下限 3 是为了拦是非题伪装，而两个复选框不是是非题——它有四种答案：都不要 / 只要 A / 只要 B / 都要。把多选也按 3 卡，直接把 G2.6 顶死：「要加哪些字段」这类题经常正好只有两个候选，拒了它就等于逼着退回成一串「要不要 A」「要不要 B」——正是多选存在的理由。

**实测踩到过**：某会话里「两个契约新增字段要哪些？」带 `tag_ids` / `reviews[].language` 两个候选，是一道完全正当的多选题。当时它被放行了，因为校验器还只在 `/qna:ask` 内生效而那个会话没跑过命令；按当时的规则它本该被拒，理由还会是「2 options is a yes/no question in disguise」——对一道多选题来说这个诊断是错的。

实践中这两个需求很少落在同一道题上：需要 preview 的是方案对比题，而方案对比题天然单选；天然多选的题选项一行一个，本就不需要并排展示实物。

## 四 · Commands

只有一个。

| 命令 | 谁能调 | 参数 | 做什么 |
|---|---|---|---|
| `/qna:ask` | 只有你 | `[话题]` 可选 | 扫描 + 对账 + 分级 + 聚合 + 逐题问 + 出决策清单，然后停 |

```yaml
# plugins/qna/commands/ask.md
name: ask
description: 所以我需要拍板什么？把待决的点全变成可点选的问题。
disable-model-invocation: true
argument-hint: [可选：只清理某个话题，如「架构」]
```

`description` 的唯一读者是你（`disable-model-invocation` 之后模型看不到它），所以写成你会在补全里认出的那句话，而不是给模型看的能力声明。

### 这个命令替代的那句 prompt

`/qna:ask` **等价于用户敲下**：

> 所以我需要拍板什么？还有哪些待办？请用问题来让我拍。

这不是类比，是本命令的定义。`ask.md` 正文开头必须写死这一句，因为它决定了扫描的重心。

**证据**：本 session 中用户三次手打同类 prompt——「还有其他问题吗？」「所以我需要拍什么？」「还有问题吗？有的话让我拍」；session `295fbbe8` 的 line 260 结尾同样是「还有问题吗？」。这是个高频固定动作。

**推论——最重要的素材往往不在 pending 文件里。** 用户敲这句话的典型时机，是刚读完我一大段散文，里面塞着"我倾向 A，但 B 也有道理"、"这个值得再想想"、"要注意 X 可能有隐患"。这些**不是我偷偷做的决定**（`qna-add` 不会记它们），而是**我已经提出、但没做成可决策形式的问题**。它们只存在于刚刚那几轮的文字里。

因此扫描必须显式包含这一类，且给近因加权（见第七节）。

**`/qna:note` 已删除。** 两头都没有用户：愿意敲 `/qna:note` 的人会直接敲 `/qna:ask`；模型有 `qna-add`（能校验能拒绝，比 skill 强）。它唯一合理的用例「先记着回头再说」已改写成记录协议 2，靠对话里一句话触发。

## 五 · Tools

### 我们提供的脚本

四个脚本，**都不许模型自己拼路径**——`--session`、`--project`、`--transcript` 全由 `SessionStart` 注入在命令行里（理由见第九节「一切走脚本」）。

```
qna-add   --session <id> --project <abs> --transcript <abs>   ← 注入，模型照抄
          --title <一行>  --chose <你选了什么>
          --alt <备选> --alt <备选> [--alt <更多>]
          --why <是什么取舍让你这么选>
          --where <file:line 或 一句原话>
          [--deferred-by-user]        协议 2 专用，见下
          [--found-by-scan]           /qna:ask 扫描侧补记专用

  Source 三态：agent（当下记的）· user-deferred（你亲口要记的）
              · scan（/qna:ask 事后补的，备选是补的不是当时比的）

  校验顺序，第一个失败即退出非零：

    --alt 少于 2 个      Refused: need at least 2 alternatives. If you
                         cannot name two a competent engineer might
                         prefer, this is an implementation detail.
    --where 两种形态都不成立
                         Refused: --where must be either a real file:line
                         or something actually said in this conversation.
    通过                 分配递增 id 后追加，回 "Recorded #4."


qna-resolve <id>  --session <id> --project <abs>
                  --result <定成了什么>  --quote <用户原话>

    --quote 缺失         Refused: no quote. If you cannot quote the user,
                         it is not settled — leave it in the queue.
    id 不存在            拒绝并列出当前所有 id
    已归档过             拒绝
    通过                 标 [x] 并追加 Result / Quote 行，回 "Resolved #4."



qna-scan    --session <id> --project <abs> --transcript <abs>  [--mark]

    无参      打印「上次扫描之后」的对话：过滤 + 开窗，见下
    --mark    把最新一条记成已扫，/qna:ask 的最后一个动作
    exit 2    transcript 读不了（模型改为扫自己的上下文）
```

**`--alt` 下限是 2 不是 1。** 条目映射为 `Chose` → 第一个选项、`Alternatives` → 其余选项，下限 1 只能产出 2 个选项，直接违反 D12「每题至少 3 个」。下限 2 才保得住。

### `--where` 接受两种落点

原设计只收 `file:line`，那是错的——`/qna` 大半价值在**对话里产生的决策**（方向、范围、取舍），它们根本没有代码落点。要求 file:line 等于把主战场排除在外。

而且防编造的理由也站不住：行号随便编一个，脚本只查文件存不存在，拦的只是"连文件名都编不出"。

```
--where "src/cache/backend.py:1"      代码落点 → 查文件存在
--where "这个先记着，回头再说"          对话落点 → 在 transcript 里 grep 验证
两者都不成立                            → 拒绝
```

**对话落点比代码落点更严**：行号可以编，一句真说过的话编不出来。

### transcript 的两个读者

jsonl 的格式依赖收在 `qna_lib.iter_turns` 一处——官方哪天改了结构只需修这一个函数。它按顺序吐出对话轮次（`uuid` / `ts` / `role` / `text` / `compacted`），**只留文本**：tool 调用、tool 结果、thinking、sidechain、`isMeta` 全丢。两个脚本共用它，一个做校验，一个做扫描。

#### `qna-transcript` — 原话校验器

```
qna-transcript --grep "<原话>"

  退出码   0  找到
           1  能读懂 transcript，但没有这句话
           2  读不了（文件不在 / 格式变了 / 解析失败）
```

`qna-add` 只看退出码：

| 退出码 | 处理 | 理由 |
|---|---|---|
| 0 | 正常记录 | |
| 1 | **拒绝** | 能读懂却找不到，就是编的 |
| 2 | **放行，标 `unverified`** | transcript 是内部格式，不该因为官方改了字段就让整个工具记不进东西 |

**怎么拿到 transcript 路径**：不能自己拼（`~/.claude/projects/` + cwd 转义是内部规则，且中途 `cd` 就错）。`SessionStart` hook 的输入 JSON 里直接给了 `transcript_path`，**随命令行注入**给 `qna-add`，再由它转交 `qna-transcript`。

**为什么不落 `.meta` 就好**：落盘要先建 `.qna/`，而这个 hook 在每个项目都跑——于是每个开过会话的项目里都凭空多出一个目录，哪怕它从没记过任何条目（实测：装上一小时，两个项目全中）。路径走命令行，`.qna/` 就只在**第一次真正记录成功后**才出现。`.meta` 仍然写，但只在目录已存在时写，且只承担两件事：`qna-transcript` 手动调用时的回退、`Stop` hook 的 `reported_max_id`。

**怎么匹配**：拿 `iter_turns` 的全部文本拼起来，归一化空白后做子串匹配。

**已知限制**：当前这一轮尚未结束的内容可能还没落盘。但验证的是**用户说过的话**，用户消息在收到时即写入，实际不受影响。

#### `qna-scan` — 扫描窗口

`/qna:ask` 的对话来源。两件事都必须是脚本，不能是判断：

**一、过滤。** 实测一个干活会话的 transcript：**总共 2916.7 KB，其中 97% 是 tool 调用、tool 结果、thinking 和元数据**，真正的一来一往只有 97 KB。滤掉噪音是「这文件根本打不开」和「一次扫描装得下」之间的差别——`iter_turns` 过完，59 KB 出头。

**二、开窗。** `.meta` 里的水位线记着上次扫到哪，从那之后读起。长会话里第二次 `/qna:ask` 因此比第一次便宜。**续读锚点用 `uuid`，`timestamp` 兜底**：uuid 精确，时间戳会重复、时钟会跳。两个锚点都失效时**重读全部**，不猜边界——多读只是慢，少读是静默丢料。

**水位线在 `/qna:ask` 的最后一步才前进**，不是第一步。提前推进意味着中途被打断的那一轮里，一整段对话在下次扫描时被跳过，而且没人报告——正是最贵的那类失败。

**遇到 compact 会明说。** 窗口里含 `isCompactSummary` 时，脚本在头部标注「本窗口跨越一次上下文压缩，下面那条摘要是压缩过的，不是原文」，模型据此在总览里注明早期细节可能失真。

**这一条推翻了 v1 原本的判断。** 当初写的是「不做 compact 恢复：等于把刚被压缩的文本又灌回上下文，一次 ask 的开销可能比整个流程还大」——那是没量过的估计。滤噪拿到 30 倍，全会话对话正文只有 59 KB，量出来之后这个反对理由不成立。

**上限有，且会报。** 默认 200 KB，超了保留最新的部分，并在头部写明丢了多少轮**且这些轮没被扫过**。一个不吭声的截断读起来就是「你已经看全了」。

**`--deferred-by-user` 标记协议 2 的来源**（你在对话里说"这个先记着"）。带此标记的条目：

- 聚合**不得**把它降级进「我按默认处理了」
- 因此也**不会**被当作琐碎项删除

否则会出现一个直接违背你指令的错误：**你明确要求记下的事，被我判定为琐碎然后删掉。**

### 提问侧闸门：`PreToolUse` 校验器

记录侧有 `qna-add` 把关，提问侧原本只有 R1–R7 七条 prompt 规则——**编不出 `--alt` 就真的过不去，给两个选项却没人拦**。这个落差用 `PreToolUse` hook 抹平。

```
PreToolUse   matcher: AskUserQuestion       ← 每个会话、每一次提问

    入参解析失败         → deny  "Refused: the question payload did not
    (__unparsedToolInput)         parse, so none of the asking rules
                                  could be checked. Almost always size
                                  — the previews are the usual culprit."
    单选 options < 3     → deny  "Refused: 2 options is a yes/no
                                  question. R2 requires >= 3."
    多选 options < 2     → deny  "Refused: 1 option is not something to
                                  choose between."
    options > 4          → deny  "Refused: tool caps options at 4."
    单选且无 preview     → deny  "Refused: every single-select question
                                  needs a preview. If you cannot think of
                                  what to show, you have not worked out
                                  what each option actually leads to."
```

`deny` 的 `permissionDecisionReason` 直接回给模型，和 `qna-add` 的拒绝文案同一套路数：**拒绝本身就是答案**。

#### 作用域：全会话，不分场合

**原设计限定在 `/qna:ask` 内**，靠一个 `.qna/<sid>.active` 标记文件开关，理由是「这些规则适合清理积压，对日常对话过于死板」。

**实测推翻了它。** 某会话 49 次提问、`/qna:ask` 从未调用，其中 3 道单选题**全部没有 preview**——R4 在命令之外的合规率是 0%。而比例是反的：`/qna:ask` 一天跑几次，普通提问一天几十次。**把最严的规则只用在最少的场合，等于没有规则。**

于是校验器改为无条件生效，`qna-mark` 脚本、`.active` 标记、`/qna:ask` 的开关两步一并删除——标记的唯一职责就是划这个作用域，作用域没了它就是死代码。

**接受的代价**：真的只有两条路的题（「要 A 还是要 B」）现在也得凑出第三个选项。这是明知代价后选的。

**顺带消掉一条静默失效路径。** 标记时代最贵的失败模式是：写标记的是模型跑的 shell（那里**没有** `CLAUDE_PROJECT_DIR`，路径必然回落到当次工作目录），读标记的是 hook（用自己 payload 里的 `cwd`）。两边各自理解「当前目录」，会话起在子目录或中途 `cd` 就错位——而**找不到标记 = 判定 `/qna:ask` 没在跑 = 全部放行**，硬闸整程失效且毫无提示。校验器不再依赖任何磁盘状态，这个口子从根上不存在了。

### 依赖的内置工具

| 工具 | 用在哪 |
|---|---|
| `AskUserQuestion` | 全部提问。`preview` 用于格式/结构类选项 |
| `Bash` | 调 `qna-add` / `qna-resolve` / `qna-scan` |
| `Read` | `/qna:ask` 读 pending 文件 |

扫描侧不用 `Read` 读 transcript：3 MB 的文件读不进来，`qna-scan` 过滤加开窗之后才是可读的量。

### 存储

`<项目>/.qna/<session_id>.md`，append-only，按项目 + session 双重隔离。

**目录懒建**：只有 `qna-add` 记进第一条、或 `qna-scan --mark` 推水位线时才建 `.qna/`。三个 hook 一律先看目录在不在，不在就不碰磁盘——它们在每个项目都跑，没这条纪律就会把空目录撒得到处都是。

```markdown
<!-- qna-pending · written by qna-add / qna-resolve · cleared by /qna:ask -->

- [ ] #4 · 2026-07-27T19:02 · 缓存后端选型
  - Chose: SQLite
  - Alternatives: 纯文件目录 / Redis / 内存 LRU
  - Why: 要跨进程共享又不想引外部依赖
  - Where: src/cache/backend.py:1
  - Source: agent
  - Verified: yes

- [ ] #5 · 2026-07-27T19:33 · 要不要支持自定义缓存目录
  - Chose: 暂不支持，写死 XDG 路径
  - Alternatives: 读环境变量 / 加 --cache-dir 参数
  - Why: 你说先记着回头再说
  - Where: 这个先记着，回头再说
  - Source: user-deferred
  - Verified: yes
```

**`Source` 与 `Verified` 两个字段是实装追加的。** `Source: user-deferred` 取代了原设计写在标题后的 `(deferred-by-user)` 后缀——聚合规则要机械地读它（`--deferred-by-user` 的条目不得降级），字段比标题里的括号可靠。`Verified: unverified` 标记 transcript 读不了时放行的那一类。

**`id` 是必须的**——`qna-resolve <id>` 靠它定位，`SessionStart` 清单段也要带它，否则模型知道有条目却无法引用。由 `qna-add` 分配递增序号，session 内唯一。

字段名英文，标题与内容跟随对话语言。`SessionStart` 顺手清理**本项目** `.qna/` 下 30 天未修改的孤儿文件。

### 分层：能用代码保证的绝不用 prompt 保证

```
  代码保证 |  记录侧  文件路径 · 时间戳 · session 隔离 · 必填字段
  (脚本    |          落点可验证（代码存在 或 原话确实说过）
   + hook) |          alt 数量下限 · 归档必须带 quote
           |  提问侧  单选 3~4 个 · 多选 >= 2 个 · preview 必须存在
           |          入参解析失败（__unparsedToolInput）直接拒
           |          （PreToolUse 校验器，全会话恒生效）
           |  落盘位置  锚点由 SessionStart 定、注入进每条命令
           |            读侧 hook 按 session id 向上定位
           |            （模型不参与任何路径计算）
           |  扫描窗口  滤掉 97% 的 tool 噪音 · 水位线由 qna-scan
           |            读写，模型看不到也算不到边界
           |  扫描侧  存活项同样经 qna-add，三道过滤在两侧
           |          都有硬闸（Source: scan 标出成色差别）
  ---------+-----------------------------------------------------
  prompt   |  这算不算一个决策点          <- 只剩这两处
  保证     |  对账判断是否已解决
```

两侧保证强度现在对等：记录侧编不出 `--alt` 过不去，提问侧给两个选项也过不去。

**「落盘位置」这一行的门槛与前两行不同：前两行拦的是错的内容，它拦的是错的地点。** 字段与数量算错会当场被拒；文件落错地方不报错——pending 文件落到别处，`SessionStart` 就读不到既有条目，悬置清单凭空消失，而且没有任何提示。**一条静默失效的路径，比十条会报错的更贵。** 所以凡是模型要算的东西，都先问一句：算错了会不会有人喊。没人喊的，交给脚本。

### v1 范围

装：

| 件 | 作用 |
|---|---|
| `/qna:ask` | 唯一命令 |
| `qna-add` | 记一条未决 |
| `qna-resolve` | 结一条 |
| `qna-transcript` | `--where` 原话校验 |
| `qna-scan` | 扫描窗口 + 水位线 |
| `SessionStart` hook | 注协议 · 注命令 · 列悬置 |
| `UserPromptSubmit` hook | 每 15 轮复推（不渲染）|
| `Stop` hook | 新条目播报（唯一渲染给用户的）|
| `PreToolUse` 校验器 | 卡住每一次 `AskUserQuestion` |
| `tests/smoke.sh` | 120 条断言 |

不装：transcript 的 compact 恢复 · 相似度去重 · 12 条上限 · 孤儿清理以外的维护逻辑

**`Stop` hook 已收进 v1，但只保留「读文件」这一半。** 原本判它性价比最低，针对的是"回溯性催促模型自查这一轮有没有漏记决策"——那种自查很弱。读文件里的条目不需要任何判断，成本近零，于是留下。

原 `[待审]` 积压提醒（条数跨 5 的倍数时提一句）先落成"条数变化时报一次"，再改成现在的**新条目才播报**：`.meta` 存 `reported_max_id`，只有 id 更高的新条目才出声。

**为什么从"报条数"改成"报新条目"。** 条数比对把两件事混成一件：记进一条，和归档一条。

归档是用户自己刚做的动作。回头告诉他"现在还剩 2 条、最新一条是 X"——X 往往是一小时前那条，跟他刚做的事无关，是**关于无事的通报**。

真正值得打断的只有一个瞬间：又替他做了一次主。所以触发条件是 id 增长，归档一律静默；同一轮里记进又归档的，一次都不播。

**为什么连 `Chose` 一起播。** 只报标题等于抛一个问句就走——"要不要用 disable-model-invocation"让人知道有东西要想，却没有可想的材料。

带上 `--chose`，最常见那条路径根本不用走 `/qna:ask`：看一眼选了什么，认了，这条就以沉默结案。`/qna:ask` 留给"我更希望是另一种"的情形。

## 七 · Workflow

### 写入侧 — 三条测试全过才记

```
  1  替代项测试   说得出至少两个有能力的工程师可能真心更偏好的做法
  2  代价测试     事后改它不止一两行：要动数据结构/接口/多处调用/已写数据
  3  意外测试     你三天后发现"这是它自己定的"会皱眉，而不是"这不废话吗"

  绝不记  用户已经说过的      <- 最严重的失败模式
          命名 · 日志措辞 · 代码放哪个文件 · 注释
          测试数据 · 格式化 · 只有一种合理写法的实现

  判据    他把事情定了 -> 不记      他把事情搁了 -> 记（协议 2）
```

### 扫描侧 — 五类来源

```
  1  我问过、你没正面回答的
  2  双方说过"稍后再定 / 先这样"的
  3  我替你默默做了选择但没请示的          <- pending 文件的主体
  4  你的表述有歧义，两种读法导出不同做法
  5  我在最近几轮里用散文提出、但没做成     <- 只在对话里，文件里没有
     可决策形式的问题、疑虑、"但是"
```

**第 5 类是 `/qna:ask` 被敲下时最常见的素材**，而它完全不在 pending 文件里——`qna-add` 只记"我做了什么决定"，不记"我提了什么问题"。典型形态：

```
  "我倾向 A，但 B 也有道理"
  "这个值得再想想"
  "要注意 X 可能有隐患"
  "如果你觉得…也可以"
  一段结尾的"还有几点提请注意：…"
```

**排序：主键依赖，次键近因。** 依赖关系仍然优先（G3.1，被别的题依赖的先问），同层之间**最近几轮产生的排在前面**——用户是读完刚才那段话才敲的命令，注意力还在那里。

### 扫描侧筛选 — 与写入侧同一套闸，但没有脚本兜底

扫描捞出候选之后，**逐条套用写入侧那三条测试和负面清单**。这不是可选的补充，是必需的：写入侧有 `qna-add` 挡着，扫描侧一个脚本都没有，全靠这份指令。**筛选强度不对等的话，整套过滤就只作用在低召回的那条路上。**

```
  三条测试   同写入侧（替代项 / 代价 / 意外），全过才成题
  负面清单   同写入侧（命名 · 日志措辞 · 文件位置 · 注释 · 测试数据
             · 格式化 · 只有一种合理写法的实现）
```

扫描侧还有三条**写入侧没有**的额外闸——它们针对的是"回看对话"这个动作特有的风险：

| | 闸 | 为什么扫描侧才需要 |
|---|---|---|
| S1 | **你已经说过的，一律不成题** | 扫描直接在你的原话上作业，是把你的指令反手做成问题的最高风险点。写入侧只是"别记"，扫描侧是"别把眼前这句话变成题" |
| S2 | **我问过、你答过的，不成题** | 那是对账的活。扫描若把它捞成候选，等于给对账制造工作量，还多一次误判机会 |
| S3 | **纯粹的风险提示不成题** | "要注意 X 可能有隐患"——如果它没有可选项、只有"知道了"，那是提醒不是决策。做成题就是逼你点一下"好的" |

S3 与第 5 类来源看似冲突，判据是：**那段散文里有没有真实的岔路。** 有岔路 → 成题；只是提醒 → 写进收尾清单的「按默认处理」栏，不占提问名额。

### 范围闸 — 开问前的第一道题

**触发条件**：待问项**跨越两个来源**——既有本轮对话新产生的（第 5 类），又有之前积压的（pending 文件里的历史条目）。

若全部来自本轮，没有范围可分，直接开问，不设闸。

**位置**：总览之后、第一道实质问题之前。总览提供的数字正是这道题的作答依据。

**题目形态**（本身也遵守 R2/R4，≥3 选项、带 preview、单选）：

```
现在有 11 条待拍板 —— 4 条是刚才这轮产生的，7 条是之前积压的。
你想处理到哪一步？

  只处理刚才这轮（4 条，1 批）
    积压的留在文件里，下次再说

  全部一口气处理（11 条，3 批）
    答完文件清空

  只处理重头的（6 条，2 批）
    顺手题一律按默认走，在收尾清单里列出来给你过目

  只挑最要紧的 3 条
    其余全部保留，不做任何默认处理
```

**这不是 D3 被否掉的那个东西。** D3 否掉的是「列出全部问题，先勾选哪几个值得问」——**逐条筛选**，那是把分类工作推回给用户。范围闸是**一道粗粒度的胃口问题**，四个选项都是现成的处理策略，你点一下就走，不需要逐条判断。

**答完之后**：所选范围之外的条目**不静默消失**，在收尾清单里单列一栏「本次未处理 · N 条」并给出标题，与 G6.3 同一原则。

### 「我按默认处理了」的两条来路，两种归宿

同一栏里的条目，**为什么没被问决定了它之后的命运**：

| 来路 | 例子 | 文件里怎么处置 | 依据 |
|---|---|---|---|
| 我判定太琐碎，不值得占一道题 | 命中日志用 debug 还是 info | **删除** | 它没通过重要性门槛，本就不该占一个决策位。留着只会每次 `/qna:ask` 都冒出来刷存在感——那正是"问一个不该问的问题" |
| 你在范围闸选了「只处理重头的」 | 过期清理什么时候跑 | **保留** | 这是真决策，只是你这轮说了先不管。你从未拍过它，下次该继续问 |

不需要给文件新增状态位——区分靠的是降级原因，写入时就已知。

**这条规则让范围闸的「只处理重头的」变得安全。** 否则选了它就等于让一批真决策按默认值静默定稿，而你从头到尾没拍过——那个选项会变成陷阱。

### 读出侧 — 七条硬规则

```
  R1  超过 4 题分批连发            绝不退回 markdown 列表        <- 核心
  R2  单选下限 3 · 多选下限 2      上限 4 · 禁是非题 · 不凑数
      重头题末位留「我没看懂这题」   唯一豁免「必须是做法」的选项
  R3  选项自解释                   专有名词要说清它是什么
  R4  所有单选题必须带 preview     并排展示实物 · 默认 single-select
  R5  重头题先解释再问             同一轮 · 紧贴题目上方 · 约一屏
      批次之间不写过程叙述          禁复盘 / 重估小作文 / 「接下来」
  R6  每答完重头题重估剩余         失效的划掉 · 变形的重写 · 新增的补上
  R7  一切提问走 AskUserQuestion   不得以散文形式提出
```

### R5 的两半不是一回事

**「重头题先解释再问」和「批次之间不写过程叙述」管的是两种文字，必须分开写。** 前者是题目的一部分：这题在争什么、为什么现在争、拍错了会怎样。后者是关于流程的旁白：刚答完那题的复盘、重估小作文、「接下来问 X」。

**曾经把这两半写成一句，结果前一半被后一半吃掉了。** 当时的措辞是「批次之间不写散文——总览是全命令唯一的叙述位置」。最后半句读起来就是禁令：既然总览是唯一能写字的地方，重头题的解释也就没地方放了。

**实测代价**：某会话两次 `/qna:ask` 共发出 12 道题，**同一条消息里带解释的 0 道，上一条消息带解释的也只有 2 道**——那 2 处还是总览表格本身，不是题目解释。细节全挤进了 `description`（最多 1260 字符）和 `preview`（最多 1131 字符），但**共享前提没有容身之处**：每个 preview 只为自己那个选项写，读完三个也拼不出「这题为什么成立」。用户的原话是「问很复杂的问题但从不先解释再问，这让我非常难回答」。

**没有解释的题比啰嗦的题更糟**，这是这条规则存在的理由。

### 两条通道：`Stop` 给人看，`UserPromptSubmit` 给模型看

这是整套 hook 输出的分界线，也是踩了三次才画准的一条线。

**哪条通道会渲染，transcript 里看得见。** 同样是 `additionalContext`，落盘形态不同，命运就不同：

```
SessionStart · UserPromptSubmit  →  attachment / hook_additional_context  →  只进模型上下文
Stop                             →  system / stop_hook_summary           →  渲染成 "Stop hook feedback"
                                                                             跟在回复下面，用户直接读到
```

**`suppressOutput` 管不住 Stop 这一路，这点已经实测。** 两条输出都带过这个 flag 整整一个版本，用户仍然把整行原样贴了回来。所以 flag 直接删掉了——**一个不起作用的开关比没有开关更糟，它让问题看起来已经处理过了**。取代它的不是另一个 flag，是一条放置规则：

```
写给模型的话  →  一律走 UserPromptSubmit（不渲染，且本轮开头就到，没有晚一轮的时差）
写给人的话    →  只放 Stop，且只放值得打断人的那一句
```

**踩过的三步，每一步都留在代码注释里。**

| 版本 | 做法 | 撞到什么 |
|---|---|---|
| 一 | 150 词指令块，结尾写「别把这个检查告诉用户」，因为以为没人看得见 | 用户把整段读完了，包括一条裸的绝对路径，反馈是「这段很奇怪」 |
| 二 | 让模型复述：「Surface this as a single short line…」 | 同一条消息出现两遍。更糟的是这句指令**留在那个会话的上下文里不会走**——改完代码几小时后，那个会话仍在每轮末尾打印旧格式的 `qna: 2 parked — /qna:ask to settle` |
| 三 | 加 `suppressOutput`，同时把文案压短「以防它不生效」 | 确实不生效。压短是对的，靠 flag 是错的 |

第二步的教训比它看起来更重：**注入进上下文的指令是不可撤回的**。改代码只影响之后发出的文本，已经进了某个会话上下文的那句，会一直被执行到 compact 或 `/clear` 为止。所以现在「不要复述」这条规则写在 `SessionStart` 的协议里（模型侧、静默通道），而不是每次跟着可见输出一起发。

**播报本身要自解释。** 最早是 `qna: 1 parked — /qna:ask to settle`，用户原话「不知道这个是啥意思」——既没说记的是什么，也没说 `/qna:ask` 会干什么。现在三行：条目名、当时选了什么、剩几条未决。

### 问完了，答案却没落地

**实测最贵的一次失败。** 某项目一个 session：

```
08:36  qna-scan              扫描
08:38  qna-add × 4           记下 7 条
08:41–08:57  AskUserQuestion × 4   问了 4 轮，用户全答了
08:56  qna-scan --mark       水位线推过这几轮
       qna-resolve           0 次
       代码                   0 行
09:13  最后一句：「你点头，我就开始写」——点头没来，session 就此结束
```

用户的原话是「聊了一大堆，但是根本没有落地下来，反而只是存了问答结果」。

**三个洞叠在一起，缺一不可。**

| 洞 | 表现 | 补法 |
|---|---|---|
| `/qna:ask` 第 8 节写着「打印决策清单然后**停**，不做修改」 | 一小时的问答产出一张表 | 改成「写回 → 报告 → 干活 → 推水位线」，顺序固定，中间不许插别的；并明写禁止以「你点头我就开始写」收尾 |
| 答案没写回，而水位线照推 | 4 个答案只活在 transcript 里，且下次扫描不会再扫到那几轮 | `QNA_RESOLVE` 提到第 8 节最前面，`--mark` 明确排在干完活之后 |
| 记过东西的 session 永久关闭提醒 | 那 7 条从记下到 session 结束无人再提 | `prompt-nudge` 拆成两种状态：**没记过**照旧复推协议，**记了没结**每 15 轮提醒写回并落地 |

**「打印然后停」当初是对的，因为它防的是另一件事**——N2「不自动执行决策」，怕的是模型拿着一张自己攒的清单自说自话地开工。

但这条规则挡在了错误的位置：用户刚刚**逐题点选**回答完，正是授权最明确的时刻。此时再问一次「要开始吗」，等于把他刚花掉的那些点击作废。

N2 现在只管两件事：scope gate 之外的活，以及 N3 说的破坏性 / 不可逆操作。

### 提醒的节奏靠「距上次多久」，不是「发过几次」

固定步长的天然写法是「发过 N 次 → 下次在 (N+1)×15」。这个写法有个 bug：**中途装插件的会话，进来时计数已经越过好几个步长**，于是「发的次数少于计数应有的次数」在连续几轮里连着成立，一口气补发一串提醒。

改法：把「上次提醒时的回复数」写进那句可见文本里，下次从文本里读回来（`qna: (\d+) replies, nothing recorded`），判据变成 `turns - last >= 15`。既无状态文件，也不会补发。这也是标记必须是纯 ASCII 的原因——transcript 会把非 ASCII 转义成 `\uXXXX` 形式，`·` 之类的字符会让匹配静默失效。

### `qna-add` 的两种拒绝含义不同

实测第三个会话：提醒催出了一次记录尝试，`--where` 传了一句凭记忆复述的话，被拒，条目就此丢掉。

问题在协议的措辞：「拒绝本身就是答案，那不是一个决策」——这话**只对 `--alt` 成立**。`--alt` 不足是在说「这是实现细节，别记」；`--where` 不成立是在说「你的引用没核对上」。两者混为一谈，会把真决策悄悄扔掉。

现在两条拒绝文案自己讲清区别，`--where` 那两条都带一句「这是对引用的判定，不是对条目的判定：真是决策就修引用重跑，别丢掉它」。提醒里也顺带说明 `--where` 收什么——**事后十几轮再回忆，`file:line` 比原话可靠得多**。

### 记录侧为什么会一条都不记

**协议只在第 0 轮注入一次，之后整条链路没有任何复发触发点。** 而唯一可能提醒的 `Stop` hook，在零条目会话里是**结构性静默**的：`.qna/` 不存在就 return、文件不存在就 return、条数没变就 return。提醒只对「已经在用这个工具」的会话存在——恰好是最不需要它的那批。

**实测**：某 54 分钟会话，注入生效、84 轮对话、49 次 `AskUserQuestion`，`qna-add` 零调用。而它确实有该记的东西，例如「所以改用真 cookie 打（脚本只打印状态码，不回显 cookie 值）」——有备选、有取舍、用户没签字。

**修法：`UserPromptSubmit` 在零条目会话里每 15 轮复推一次协议。** 起初挂在 `Stop` 上，后来整条挪走——这段文字通篇是对模型说的（脚本名、`--where` 收什么），而 `Stop` 会渲染给用户，等于让人读一封不是写给他的信。四个设计约束：

| 约束 | 怎么满足 |
|---|---|
| 不能被用户读到 | 走 `UserPromptSubmit`，落成 `attachment` 不渲染。这是它从 `Stop` 挪走的唯一原因 |
| 不能写盘 | 提醒次数**从 transcript 里数**——`additionalContext` 本身会落成 `hook_additional_context` 条目，已经是磁盘上的记录，不需要第二份。这条是硬要求：hook 无处可写而不在每个开过会话的项目里留下 `.qna/` |
| 不能把判断权搬走 | 提醒只把协议重新拉回视野、把命令行摊开。**「模型干活中途主动打断自己、自我判定」是设计本身，不是要绕开的东西** |
| 不能变成注水机 | 提醒里明写「一条都不过关也是个真答案，别说话，往下走」 |

**当年砍掉的是每轮提醒**，理由写在注释里：「回顾式自检很弱，每轮一次的成本换来的东西很少」。现在量出了对照组：换来的是 0 条。固定 15 轮步长是另一个成本档——每 15 轮一句话，且因为不渲染，用户一次都不会看到。

**步长固定，不做 15 / 45 / 90 这种递减。** 第 200 轮做的决定不比第 15 轮的更不值得记；会衰减的提醒把长会话的长尾整段放空。

R1 / R2 / R4 由 `PreToolUse` 机械保证，R3 / R5 / R6 / R7 靠 prompt。**R7 是唯一一条 hook 拦不住的**——它禁的是"不调用 `AskUserQuestion`"，而 hook 只在工具被调用时才触发，管不了没发生的调用。

### 重头题末位那个选项

**「我没看懂这题」占最后一个位置**，前面三个是实打实的做法，加起来正好用满上限 4。它是**唯一豁免「每个选项必须是一个能落地的做法」的选项**，因为它回答的不是题目本身。

**选它不是弃权，是一份缺陷报告——说明 R3 失效了。** 所以正确反应是重写：换掉行话、把专有名词摊开、用一个具体场景替掉抽象说法。同一个题干原样再发一遍是最差的处理。

**为什么不靠自由文本框。** 兜底一直都在（带 preview 的并排布局里它渲染成 `Notes:` 那行，不是第四个选项），但用它要打字，而打字正是这条命令要消灭的东西（G1.1）。看不懂一道题的人，不该还得写一段话来解释自己看不懂。

**顺手题不加。** 顺手题本来就不需要背景，看不懂只说明题干没写好，自由文本框足够覆盖。

**证据**：单个会话里用户三次交出 `(no option selected) notes: 没太懂` —— 其中两次是我用内部词汇造的题（「窗口外的开放项」「非目标」）。兜底能用，但每次都要他打字，而且这类失败原本应该由我来修，不该由他来描述。

## 八 · 使用样例

**场景**：你让我给 `arkcli` 加响应缓存，我干了 40 分钟你没打断。

**本节命令一律省掉注入前缀。** 实际形态是 `SessionStart` 注入的完整命令行，模型整行照抄：

```
/Users/…/plugins/cache/qna-marketplace/qna/0.2.0/scripts/qna-add \
    --session 8026af30 --project /Users/…/arkcli \
    --title "缓存后端选型" …
```

下面为可读性只写 `qna-add --title …`，省掉的正是这两个注入参数。

### 干活期间 · 记录

代码落点，`--where` 指向真实文件：

```
$ qna-add --title "缓存后端选型" --chose "SQLite" \
          --alt "纯文件目录" --alt "Redis" \
          --why "要跨进程共享又不想引外部依赖" \
          --where "src/cache/backend.py:1"
Recorded #1.
```

想记"命中日志用 debug 还是 info"，只想得出一个替代项：

```
$ qna-add --title "命中日志级别" --chose "debug" \
          --alt "info" --why "默认不打印" \
          --where "src/cache/store.py:44"
Refused: need at least 2 alternatives. If you cannot name two a
competent engineer might prefer, this is an implementation detail.
```

**被挡回来了，我不绕路。** 这不是靠读了"请勿记录琐事"然后自觉。

你说「缓存目录要不要支持自定义？这个先记着，回头再说」——对话落点，没有任何代码：

```
$ qna-add --title "要不要支持自定义缓存目录" \
          --chose "暂不支持，写死 XDG 路径" \
          --alt "读环境变量" --alt "加 --cache-dir 参数" \
          --why "你说先记着" \
          --where "这个先记着，回头再说" \
          --deferred-by-user

  qna-transcript --grep "这个先记着，回头再说"  →  exit 0
Recorded #5.
```

**这句话我编不出来**，脚本在 transcript 里对上了才放行。

### 干活期间 · 就地归档

你 19:41 顺口说「TTL 5 分钟就行」：

```
$ qna-resolve 3 --result "300 秒" --quote "5 分钟就行"
Resolved #3.
```

`--quote` 必填。引不出原话就不许归档，条目留在队列里。

### 触发过一次 compact

`SessionStart` 以 `compact` matcher 重跑，`session_id` 不变 → 协议、四条注入命令、悬置清单（带 id）重新注入，`.meta` 里的 `transcript_path` 也刷新。压缩前记的一条没丢。锚点由 `find_session_dir` 重新定位到既有文件所在目录，即使这期间工作目录变过也不会分叉出第二个 `.qna/`。

### 你敲 `/qna:ask`

跑 `qna-scan` 拿到「上次扫完之后」的对话（2916.7 KB 的 transcript 滤成 59 KB，再按水位线开窗）+ 读 pending 文件 → 合并去重 → 对账 → 分级 → 聚合 → 总览：

**扫到 11 条，7 条要问。**

**等你拍的 · 7**

| # | 分级 | 题目 |
|---|---|---|
| 1 | 重头 | 缓存键要不要纳入认证身份 |
| 2 | 重头 | 写入失败静默降级还是出声 |
| 3 | 重头 | 并发写怎么处理 |
| 4 | 顺手 | 过期清理的触发时机 |
| 5 | 顺手 | 缓存统计怎么暴露 |
| 6 | 顺手 | 要不要支持自定义缓存目录（你说过先记着） |
| 7 | 顺手 | 缓存命中率要不要进 metrics |

**不用管的 · 4**

| 条目 | 归属 | 依据 / 理由 |
|---|---|---|

### 结构

仓库自身就是 marketplace，插件放在 `plugins/` 下：

```

├── .claude-plugin/
│   └── marketplace.json        name: qna-marketplace
├── plugins/qna/
│   ├── .claude-plugin/
│   │   └── plugin.json         name: qna
│   ├── commands/
│   │   └── ask.md              → /qna:ask

│       ├── stop-count.py       新条目播报（唯一会渲染给用户的输出）
```

**脚本是 Python 不是 shell。** 要解析 jsonl、读写 json、按格式往回写条目——这些用 shell 写出来的东西没人愿意改。hook 的三个入口也一并用 `.py`，免得同一套逻辑分两种语言。运行时只依赖 `python3`，插件本身零第三方依赖。

### hooks.json

```json
{
  "hooks": {
    "SessionStart": [
      { "matcher": "startup|resume|clear|compact",
        "hooks": [{ "type": "command",
                    "command": "\"${CLAUDE_PLUGIN_ROOT}\"/scripts/session-start.py" }] }
    ],
    "UserPromptSubmit": [
      { "hooks": [{ "type": "command",
                    "command": "\"${CLAUDE_PLUGIN_ROOT}\"/scripts/prompt-nudge.py" }] }
    ],
    "Stop": [
      { "hooks": [{ "type": "command",
                    "command": "\"${CLAUDE_PLUGIN_ROOT}\"/scripts/stop-count.py" }] }
    ],
    "PreToolUse": [
      { "matcher": "AskUserQuestion",
        "hooks": [{ "type": "command",
                    "command": "\"${CLAUDE_PLUGIN_ROOT}\"/scripts/pre-tool-use.py" }] }
    ]
  }
}
```

### 脚本路径必须运行时注入 —— 不解决整套跑不起来

模型是用 `Bash` 调 `qna-add` 的。但脚本住在插件缓存目录里：

```
~/.claude/plugins/cache/qna-marketplace/qna/<版本>/scripts/qna-add
```

**这个路径不在 `PATH` 上，而且带版本号——每次插件更新都会变。** 所以：

- 协议文本里**不能**写死路径
- 也**不该**往 `~/.local/bin` 塞软链——那是全局副作用，与本设计一直守的原则相抵

正确做法：**`session-start.py` 生成注入文本时，把自己所在目录的绝对路径填进去。** hook 脚本天然知道自己在哪（`$(dirname "$0")`），`${CLAUDE_PLUGIN_ROOT}` 也由 Claude Code 在调用时给出。于是每个 session 注入的协议里带的都是当次有效的真实路径：

```
  qna-add 的完整路径每 session 由 SessionStart 注入，形如
  /Users/…/plugins/cache/qna-marketplace/qna/0.1.0/scripts/qna-add
```

`pre-tool-use.py` 和 `session-start.py` 自己不受影响——它们的路径由 `hooks.json` 里的 `${CLAUDE_PLUGIN_ROOT}` 解析，Claude Code 负责替换。

### 一切走脚本 —— 项目目录也必须注入，不能让模型算

脚本路径要注入，这一条原设计就写对了。漏掉的是**另一半：`.qna/` 在哪**。原方案让模型自己拼 `${CLAUDE_PROJECT_DIR:-$PWD}/.qna/<sid>.md`，实测三处不成立：

| 事实 | 后果 |
|---|---|
| 模型跑命令的那个 shell 里**没有** `CLAUDE_PROJECT_DIR`（已实测：未设置） | 路径必然回落 `$PWD`，"项目根"这个概念在写侧根本不存在 |
| hook 侧用 payload 里的 `cwd`，与 `$PWD` 是两个独立来源 | 会话起在子目录或中途 `cd`，写侧与读侧指向不同目录 |
| 写侧要新建文件 | `.qna/` 尚不存在时，一句 shell 重定向连父目录都建不出来 |

三条都通向同一个结果，而且是最坏的那种：**写侧与读侧各写各的目录，两边都「成功」，没有一处报错。** `SessionStart` 读不到既有条目，悬置清单凭空消失；`qna-scan` 读不到水位线，把整个会话重扫一遍。全都是静默的。

修法一句话：**凡是要落在磁盘上的位置，都由脚本算、由注入带，模型只照抄。**

```
SessionStart 定锚一次:  find_session_dir(payload.cwd, sid)
                        已有该 session 文件的目录优先，否则用 cwd

注入四条，每条都带绝对 --project:
  QNA_ADD      记录（并带 --transcript）
  QNA_RESOLVE  归档
  QNA_SCAN     扫描窗口 + 水位线（并带 --transcript）
  QNA_FILE     pending 文件的绝对路径，供 Read

hook 读侧:  find_session_dir 按 session id 逐级向上找
            文件名带 session id → 命中即证明是对的目录
            撞不到别人的 .qna/（那里不会有本 session 的文件）
```

注入不是为了少打几个字——**它是把一个静默失效的口子换成一个不可能拼错的调用。**

### 安装

```shell
# 一条 curl（装 main）
curl -fsSL https://raw.githubusercontent.com/jinhuang712/claude-code-qna/main/reinstall.sh | bash

# 或会话内两条
/plugin marketplace add jinhuang712/claude-code-qna
/plugin install qna@qna-marketplace
```

装完必须**重开会话**——协议走 `SessionStart`，当前会话拿不到。

### 重装：`reinstall.sh`

卸载 → 移除 marketplace → 铲缓存克隆 → 重装 → 校验。存在的理由是一个陷阱：**`claude plugin update` 只比 `plugin.json` 里的 `version` 字符串，不 git pull 缓存里那份克隆**——改了插件却没提版本号，它回报 "already at the latest" 然后什么都不做。

在 clone 里跑装的是**工作区当前状态**（含未 commit 的改动），且 `tests/smoke.sh` 不过就拒绝安装：

```shell
bash reinstall.sh              # 有仓库就装工作区，否则装 main
bash reinstall.sh --remote     # 强制装 main
bash reinstall.sh --local      # 强制装工作区
```

### 卸载

```shell
claude plugin uninstall qna@qna-marketplace
claude plugin marketplace remove qna-marketplace
```

**全局副作用只有插件机制固有的那两条**，任何插件都一样：`~/.claude/settings.json` 里的 `enabledPlugins["qna@qna-marketplace"]` 与 `extraKnownMarketplaces["qna-marketplace"]`——`marketplace add` 的输出里明说 "declared in user settings"——上面两条命令会各自删掉。除此之外不改 `CLAUDE.md`、不往 `PATH` 放东西、不动 shell 配置。

**但项目里有残留**：用过 `/qna` 的每个项目都留着一个 `.qna/` 目录。它被自身的 `.gitignore` 忽略、不进版本库，但卸载插件不会删它。要清就 `find ~ -type d -name .qna -prune -exec rm -rf {} +`。

### 迭代

改完源码跑 `bash reinstall.sh`，然后重开会话。

`claude plugin marketplace update` 只刷新 marketplace 元数据，`claude plugin update` 只比版本号——两者都可能让改动落不进去，`reinstall.sh` 铲缓存是唯一稳的路。
